# Initial Data Dictionary

**Status:** Provisional local schema; includes one-time Airtable pilot fields/relationships, not a production contract
**Date:** 2026-09-30

Current Airtable source vocabulary is `Setor`, `Team`, `Task`, `Subtask`, `Meeting`, and `Document`. Setor also carries Project, Team also carries Person, and Subtask also carries Task for compatibility. See [airtable-mapping.md](airtable-mapping.md) for the current source field/relationship mapping and migration evidence.

Every node written by the package is keyed and queried by `workspace_id`. The first deployment is single-user and local. `workspace_id` is therefore a data partition and not a substitute for multi-user authorization.

| Label | Required properties | Optional properties in current implementation | Identity |
|---|---|---|---|
| `Workspace` | `id`, `created_at` | `name` | `id` unique |
| `Project` | `workspace_id`, `id`, `name`, `source_system`, `source_id`, `created_at`, `updated_at` | `status`, `summary`, `start_at`, `due_at` | `(workspace_id, id)` unique |
| `Task` / `Subtask:Task` | `workspace_id`, `id`, `name`, `source_system`, `source_id`, `created_at`, `updated_at` | `status`, `priority`, `description`, `updates`, `drive_folder_url`, `due_at`, `completed_at`, `complete`, `date`, `source_option_id` | `(workspace_id, id)` unique per label |
| `Client` | `workspace_id`, `id`, `name`, `source_system`, `source_id`, `created_at`, `updated_at` | `external_ref`, `website` | `(workspace_id, id)` unique |
| `Partner` | `workspace_id`, `id`, `name`, `source_system`, `source_id`, `created_at`, `updated_at` | `external_ref`, `website` | `(workspace_id, id)` unique |
| `Person` | `workspace_id`, `id`, `name`, `source_system`, `source_id`, `created_at`, `updated_at` | `external_ref`, `email`, `role`, `aliases` | `(workspace_id, id)` unique |
| `Setor:Project` | Same as Project | Project fields plus `project_lead_text`, `legacy_external_record_id`, `related_projects_text` | Both compatibility and Setor uniqueness constraints |
| `Team:Person` | Same as Person | Person fields plus `bio`, `photo_urls`, `slack_dm_url` | Both compatibility and Team uniqueness constraints |
| `Meeting` | Entity/source identity, name, created/updated timestamps | `date`, `notes`, `link`, `status`, `calendar_event_id`, `calendar_status`, `attachment_urls` | `(workspace_id, id)` unique |
| `Document` | `workspace_id`, `id`, `title`, `status`, `notes`, `attachment_metadata`, source identity, `updated_at` | `source_uri`, `mime_type`, `checksum` | `(workspace_id, id)` unique; source tuple identifies repeat ingestion |
| `DocumentChunk` | `workspace_id`, `id`, `ordinal`, `text`, `locator`, `embedding`, `embedding_model`, `embedding_dimensions`, `updated_at` | — | `(workspace_id, id)` unique |

All entity labels support source-table provenance fields from the mapping document. The current Airtable snapshot populates Meeting and Document properties from structured source rows. A separate, explicit local indexing run created derived `Document` nodes (`source_system=airtable-text-index-v1`) for current Setor, Task, Subtask, Meeting, and Document record text. Each derived node uses the Airtable record ID as `source_id`, a stable source locator, and a `RELATES_TO` link to its original entity. Document metadata fields include title/status/notes/attachment metadata/source URI/MIME type. Attachment content was not imported.

## Relationships

| Relationship | Direction | Intended use and metadata |
|---|---|---|
| `CONTAINS` | Workspace → project/entity/document | Workspace ownership/grouping; generated by upsert/ingestion |
| `HAS_TASK` | Project → Task | Project task membership; `provenance`, `review_state`, `updated_at` |
| `BELONGS_TO` | Task → Project | Explicit inverse project membership; same link metadata |
| `HAS_SUBTASK` | Task → Task | Parent task to its checklist/subtask item; same link metadata |
| `FOR_CLIENT` | Project → Client | Project client association; same link metadata |
| `WITH_PARTNER` | Project → Partner | Project partner association; same link metadata |
| `ASSIGNED_TO` | Person → Task | Task assignment; same link metadata. Airtable collaborator display names are preserved in the matched Person's `aliases`; source collaborator IDs are stored on imported relationship metadata. |
| `PARTICIPATES_IN` | Person → Project | Project participation; same link metadata |
| `LEADS` | Person → Project | Explicit project leadership, distinct from general participation; same link metadata |
| `RELATES_TO` | Document → Project/Task/Client/Partner/Person/Meeting/Document | Explicit document association; provenance and review state are recorded |
| `HAS_CHUNK` | Document → DocumentChunk | Document text split into cited chunks |

Allowed link provenance values are `USER_LINKED`, `IMPORTED`, and `EXTRACTED`. Review state values are `USER_LINKED`, `IMPORTED`, `PROPOSED`, and `REVIEWED`. Extracted links should normally start as `PROPOSED`; current tools do not run automatic entity extraction.

## Identity, history, and limitations

- Project/entity IDs are supplied by the caller and must be stable within a workspace. Source system and source ID are stored separately for lineage.
- Derived ingestion Document IDs are deterministic UUIDv5 values from workspace, source system, and source ID; pre-existing Airtable Document entities keep their Airtable record IDs. Chunk IDs include ordinal and chunk text digest.
- Re-ingestion with identical document source/content keeps stable identities. Changed content replaces chunks for that document. The current implementation does not preserve old document versions.
- Current upserts replace the supported entity properties. The current slice has no `Claim` node, general event log, alias-resolution/merge model, `valid_from`/`valid_to` history, retention job, or multi-user permission model.
- Task state is stored as a property and returned by a structured Cypher query. Historical state is not retained in this first slice.
- Text locators use 1-based source line ranges. PDF page, Word section, image, table, and audio locators are outside the initial scope.
- The schema and indexes are initial implementation decisions for a local synthetic demonstration. They are not a production migration contract.
